## Что внутри

С версии 2.0 сервис — модульный монолит на **модулях EAMS**: учётные записи, сессии, настройки,
почта и журнал действий — готовые модули из репозиториев `danrey-bilo/module-*`, подключённые подмодулями git с
закреплёнными версиями. Своё у проекта — хост, модуль Key Manager Plus и веб-панель.

| Проект | Что делает |
|---|---|
| `EmailSslSender.Api` | Хост: конвейер запросов (из модуля хостинга), движок прав проекта, строки журнала в лог, команды консоли, прежние миграции и мост к модулям, набор миграций проекта, отдача веб-панели |
| `EmailSslSender.Web` | Веб-панель: React + TypeScript (Vite) — вход с 2FA, рассылка, Key Manager, почта, пользователи |
| `EmailSslSender.Modules.KeyManager` | Опрос ManageEngine Key Manager Plus, подписки на сертификаты, рассылка файлов сертификата письмом; свой набор миграций |
| `modules/core` | Ядро модулей: контракты (почта, настройки, журнал, права, учётные записи), общий `AppDbContext`, коды ошибок, проверка зависимостей модулей при старте |
| `modules/crypto` | Мастер-ключ, конверт секретов AES-GCM, подпись значений (HMAC) |
| `modules/hosting` | Конвейер: номер обращения, конверт ошибок, контекст журнала, личность запроса, фильтр прав, пределы частоты, проверка готовности, безопасный вывод исключений в лог |
| `modules/identity` | Учётные записи, пароли (Argon2id), вход, TOTP, коды письмом, приглашения, сброс пароля, блокировка, переподтверждение |
| `modules/tokens` | Сессии: непрозрачные токены доступа и обновления, ротация, обнаружение кражи, отметка переподтверждения, список своих сессий |
| `modules/settings` | Настройки установки в базе (`system_settings`), справочник с границами и умолчаниями |
| `modules/mail` | SMTP через MailKit, очередь писем в базе, вложения, пределы частоты, шаблоны на трёх языках, рамка письма, зашифрованный и привязанный к серверу пароль SMTP |
| `modules/audit` | Журнал действий в базе (`audit_log`): только дописывается, цепочка хешей, отказы прав своим подключением, чтение и выгрузка через API |
| `EmailSslSender.Modules.KeyManager.Tests`, `EmailSslSender.IntegrationTests` | Около 320 тестов: модуль Key Manager и живые проверки хоста на PostgreSQL в Testcontainers. Модули EAMS проверяются своими тестами в своих репозиториях |

Модули подключаются в [Program.cs](../EmailSslSender.Api/Program.cs) цепочкой
`AddIdentityModule()` → `AddTokensModule()` → `AddSettingsModule()` → `AddMailModule()` →
`AddKeyManagerModule()`. Модуль не трогает хост и соседей: свои таблицы, настройки, шаблоны писем,
события журнала и пределы частоты он объявляет через контракты `modules/core`, а чего ему не хватает
(почты, настроек, крипты), называет проверка ядра при старте — сервис не поднимется с недостающей
зависимостью.

### Модули EAMS подмодулями

Модули EAMS живут каждый в своём репозитории `danrey-bilo/module-<имя>` и подключены подмодулями
git в каталог `modules/<имя>`. Используются только нужные проекту: ядро, крипта, хостинг, учётные
записи, сессии, настройки и почта (журнал, доступ, хранилища, устройства и прочие модули EAMS не
подключены). Версия каждого **закреплена коммитом метки** и сама не обновляется:

| Каталог | Репозиторий | Метка |
|---|---|---|
| `modules/core` | `module-core` | `v0.10.0` |
| `modules/crypto` | `module-crypto` | `v0.5.0` |
| `modules/hosting` | `module-hosting` | `v0.6.1` |
| `modules/identity` | `module-identity` | `v0.10.1` |
| `modules/tokens` | `module-tokens` | `v0.8.2` |
| `modules/settings` | `module-settings` | `v0.8.2` |
| `modules/mail` | `module-mail` | `v0.10.0` |
| `modules/audit` | `module-audit` | `v0.9.2` |

Клонировать вместе с модулями (репозитории модулей закрытые — нужен доступ к ним):

```bash
git clone --recurse-submodules https://github.com/danrey-bilo/email_ssl_sender.git
```

В уже склонированном:

```bash
git submodule update --init
```

Перейти на другую версию модуля — только явно: перейти в подмодуле на метку и закоммитить новый
коммит подмодуля в этом репозитории. Затем — полный прогон тестов: у модуля могли появиться новые
миграции и новые требования к хосту.

```bash
git -C modules/mail fetch --tags
```

```bash
git -C modules/mail checkout v0.10.0
```

```bash
git add modules/mail
```

**Сборка образа в GitHub Actions** (`.github/workflows/release.yml`) забирает подмодули секретом
репозитория `MODULES_TOKEN`: токен задачи читает только свой репозиторий, а модули закрытые. Токен —
fine-grained, владелец `danrey-bilo`, доступ к репозиториям `email_ssl_sender` и восьми `module-*`,
право `Contents: Read-only`: GitHub → Settings → Developer settings → Fine-grained tokens, затем в
репозитории Settings → Secrets and variables → Actions → `MODULES_TOKEN`. Локальная сборка образа
(`docker compose build`) берёт модули из рабочей копии: подмодули должны быть забраны.

Модули EAMS по умолчанию ведут себя как в EAMS; поведение версии 1.x проект возвращает опциями в
`Program.cs`:

| Модуль | Опция | Значение | Зачем |
|---|---|---|---|
| identity | `TotpIssuer` | `EAMS ssl sender` | Подпись записи в приложении-аутентификаторе |
| identity | `RefreshCookieName` | `__Host-sender-refresh` | Прежнее имя куки |
| identity | `RequireAuthenticatorForEveryone` | да | Приложение-аутентификатор обязательно всем; код письмом пускает только в настройку |
| identity | `AuthenticatorExcludesEmailCode` | да | У кого подключено приложение, код письмом не принимается |
| identity | `ChallengeCodeAttempts` | 5 | Не больше 5 кодов на одну попытку входа |
| identity | `RefreshCookieStaysCookie` | да | Половина обновления из куки уходит только кукой |
| identity | `LastSuperuserCountsOnlySignInCapable` | да | «Последний администратор» — только тот, кто может войти |
| identity | `PasswordHashConcurrency` / `PasswordHashQueueLimit` | 4 / 32 | Потолок памяти под Argon2 (64 МиБ на хеш) |
| identity | `Features.TrustedClients`, `ExtensionSignIn`, `Directory`, `StepUpEmail` | выкл. | Нет доверенных браузеров, расширения, справочника людей; переподтверждение — только приложением |
| tokens | `Features.ApiKeys`, `DeviceTokens`, `DownloadTickets` | выкл. | Ключей интеграции, токенов машин и билетов скачивания проекту не нужно |
| settings | `Features.UserPreferences` | выкл. | Личных предпочтений в панели нет |
| mail | `ProductName` | `EAMS ssl sender` | Имя в подписи письма и отправитель по умолчанию |
| mail | `Frame` | да | «Здравствуйте!» … «Спасибо,» и имя сервиса в каждом письме |
| mail | `BindSmtpPassword` | да | Пароль SMTP уходит только тому серверу, порту, защите и логину, для которых введён |
| mail | `Html` | да | Письмо уходит двумя частями — текстом и HTML; перечень сертификатов — таблицей |
| mail | `RunMaintenance` | да | Уборка отправленных писем и стирание вложений у неотправленных |

| audit | `Features.MassRevealDetection` | выкл. | Детектору нужен Redis; показ ключа и так пишется строкой журнала |
| audit | `StrictActionCatalog` | в разработке | Необъявленное событие в разработке и тестах — ошибка, в бою — предупреждение |

Свои решения проекта поверх модулей:

- **Движок прав** — [AdministratorPermissions.cs](../EmailSslSender.Api/Infrastructure/AdministratorPermissions.cs):
  ролей нет, любая активная учётная запись может всё. Каждая учётная запись к тому же
  суперпользователь: модуль учётных записей разрешает распоряжаться суперпользователем только
  суперпользователю, а в проекте администраторы равны.
- **Журнал** — [LogAuditWriter.cs](../EmailSslSender.Api/Infrastructure/LogAuditWriter.cs): строки
  `audit` в логе вместо модуля журнала EAMS. Значения изменений пишутся только у событий настроек и
  Key Manager Plus; у прочих — имена полей (у учётных записей там адреса почты). Из решений о праве
  пишутся только отказы.
- **Окно свежего кода — 10 минут**: умолчание модуля 5, значение 10 кладёт набор миграций проекта
  (`EmailSslSender.Api/Schema`), администратор меняет его на экране «Безопасность».
- **Ссылка приглашения не принимается в адресе** (`GET /api/activation?token=` → 405,
  [TokenInAddressGuard.cs](../EmailSslSender.Api/Infrastructure/TokenInAddressGuard.cs)): модуль держит
  этот путь ради клиентов EAMS, панель шлёт токен телом.
- **Пределы частоты** — числа для классов путей, которые объявили модули, и общие потолки на вход и
  активацию со всех адресов ([RateLimitGroups.cs](../EmailSslSender.Api/Infrastructure/RateLimitGroups.cs)).
- **Письмо с сертификатом — вид на число файлов** (`certificate_delivery_1` … `_9`): модуль почты
  вырезает переводы строк из подставляемых значений, поэтому список файлов живёт в шаблоне, строка на
  файл.

### Схема базы: прежние миграции, мост и наборы модулей

Каждый модуль несёт свой набор миграций и свою таблицу истории `__ef_history_<модуль>`; набор проекта
`sender` идёт последним. Команда `migrate`
([SchemaMigrator.cs](../EmailSslSender.Api/Infrastructure/SchemaMigrator.cs)) проходит под одним
замком:

1. **Новая установка** — выполняет базовые миграции модулей, затем остальные.
2. **Установка 1.x** — дотягивает прежние миграции хоста (`__EFMigrationsHistory`) до моста
   `ModulesBridge`. Мост доводит прежнюю схему до базовых миграций модулей: недостающие колонки,
   ограничения и индексы, таблица `user_preferences`; каждая учётная запись становится
   суперпользователем; неотправленные письма умирают (их тела запечатаны прежним конвертом), прежние
   вложения снимаются. Затем базовые миграции модулей **отмечаются** применёнными (схема уже есть),
   остальные выполняются.
3. **Перекладка секретов** ([LegacySecrets.cs](../EmailSslSender.Api/Infrastructure/LegacySecrets.cs)):
   конверт модулей тот же по устройству и мастер-ключу, но с другими строками разделения ключей
   (`eams:` вместо `sender:`). Секреты TOTP, пароль SMTP и ключ API Key Manager Plus открываются
   прежним конвертом и запечатываются конвертом модулей. Идемпотентно: открывшееся конвертом модулей
   не трогается, повторный `migrate` ничего не меняет.

Что две дороги дают одну схему, проверяет тест `ModulesBridgeTests` сравнением каталога; там же —
что секреты после перекладки открываются.

## Модель доступа

- **Каждая учётная запись — администратор и суперпользователь.** Ролей и прав нет. Кто вошёл, тот
  может всё (движок прав проекта — `AdministratorPermissions`).
- **Закрыто по умолчанию.** Каждое действие объявляет доступ: `[PublicEndpoint("причина")]`,
  `[AuthenticatedEndpoint("причина")]` или `[RequirePermission(...)]`. Публичны только вход,
  обновление токена, второй шаг входа, активация, сброс пароля и проверки здоровья. Проверяет это
  фильтр прав модуля хостинга (`PermissionFilter`): невошедшему — 401, действию без объявления —
  403 всем. Тест `ЗакрытоПоУмолчанию` обходит все действия и требует 401 от каждого непубличного.
- **Второй фактор обязателен.** Основной фактор — приложение-аутентификатор (TOTP: Google
  Authenticator, Aegis, 1Password и подобные).
  - Первый вход (аутентификатора ещё нет) даёт **сессию настройки**: в ней открыто только
    подключение аутентификатора и смена своего пароля. Всё остальное отвечает
    `403 TWO_FACTOR_ENROLLMENT_REQUIRED`. Если почта настроена, перед сессией настройки
    приходит код письмом: одного пароля для неё мало.
  - **У кого аутентификатор подключён, код письмом не принимается.** Иначе почтовый ящик
    давал бы и сброс пароля, и второй фактор — то есть весь вход. Потерян телефон — второй
    фактор снимает другой администратор («Пользователи») или команда `reset-superadmin-2fa`.
  - На одну расписку входа — не больше 5 кодов, дальше вход начинается заново с пароля.
    Неудачи считаются атомарно до проверки: параллельные запросы лишних догадок не дают.
- **Свежий код перед важными действиями** (решение владельца, 2026-10-20). Действия с пометкой
  `[RequireRecentSecondFactor]` — выгрузка сертификата и ключа, ключ API, пароль SMTP и проверочное
  письмо, подписки, управление пользователями (включая правку имени), любое изменение настроек
  (`PATCH /api/settings/system`) — и смена своего пароля требуют кода, подтверждённого в ЭТОЙ сессии
  за последние `auth.step_up_minutes` минут (в проекте 10); иначе `403 SECOND_FACTOR_REQUIRED` с
  `details.window_minutes`. Панель сама спрашивает код и повторяет запрос. Вход с кодом уже свежий;
  обновить — `POST /api/me/step-up` с кодом из приложения. Почему и подписки: иначе код на
  скачивание обходился бы добавлением своего адреса в рассылку.
- **Последнюю активную учётную запись нельзя отключить или удалить** (`409 LAST_SUPERADMIN`):
  иначе в систему некому будет войти.
- **Пароль администратор не задаёт.** Новую учётную запись заводят приглашением, и пароль
  человек задаёт сам по ссылке. Исключение — первая учётная запись: её заводит консольная
  команда.

## Запуск на сервере

Нужны Docker с Compose v2 и bash (на Windows подойдёт Git Bash или WSL). Все команды
выполняются из корня репозитория.

**1. Секреты.** Скрипт создаёт `secrets/sender_master_kek` (мастер-ключ, 32 случайных байта)
и `secrets/sender_postgres_password`. Существующие файлы он не перезаписывает никогда.

```bash
./scripts/gen-secrets.sh
```

> ⚠ Папка `secrets/` в git не попадает. Мастер-ключ храните отдельно от копий базы: без него
> пароль SMTP и тела писем в очереди не расшифровать, а вместе с ним — расшифровать.

**2. Туннель Cloudflare.** Наружу сервис выходит через Cloudflare Tunnel: служба
`cloudflared` в том же `docker compose` держит исходящее соединение с Cloudflare, и открытых
портов на сервере не нужно. Токен берётся в Cloudflare: Zero Trust → Networks → Tunnels →
туннель → Install connector, строка после `--token`. Скрипт спрашивает его скрытым вводом и
кладёт в файл секрета `secrets/cloudflare_tunnel_token`:

```bash
cp .env.example .env              # в нём COMPOSE_PROFILES=tunnel
./scripts/set-tunnel-token.sh
```

> ⚠ Токен — только файлом секрета: переменная окружения видна в `docker inspect` и
> `/proc/1/environ`, а с токеном любой поднимет второй коннектор туннеля и получит часть трафика.

В Cloudflare у туннеля добавьте **Public Hostname**:

| Поле | Значение |
|---|---|
| Subdomain / Domain | ваш адрес, например `sender.example.com` |
| Service → Type | `HTTP` |
| Service → URL | `api:8001` |

`api:8001` — это имя службы API во внутренней сети compose, а не адрес сервера: `cloudflared`
стоит в одной сети с API. TLS для браузера даёт Cloudflare. Адрес клиента приложение берёт из
заголовков туннеля: им верит только сеть `edge`, где есть лишь `cloudflared` и API. Поэтому
предел попыток входа считается по настоящему адресу человека.

После первого входа в панели задайте **Почта → Адрес сервиса** = `https://sender.example.com`:
из него собираются ссылки в письмах.

**3. Образ.** Готовый — из релиза (`docker compose pull api`); из исходников — `docker compose build --pull` (`--pull` забирает свежие базовые образы с исправлениями безопасности; без него Docker соберёт на старой копии из кэша).

**4. Схема базы.** Обычный старт на отставшей схеме отказывается работать, поэтому схему
накатывают только этой командой, в том числе после каждого обновления кода.

```bash
docker compose run --rm migrate
```

Служба `migrate` — одноразовая (профиль `tools`) и единственная, у которой есть пароль
владельца схемы `sender` (суперпользователь в образе `postgres`). Кроме миграций она заводит
или обновляет роль `sender_app`, которой ходит служба `api`:

| Что может `sender_app` | Чего не может |
|---|---|
| `SELECT`, `INSERT`, `UPDATE`, `DELETE` в схеме `public`, последовательности | `CREATE`, `ALTER`, `DROP`, `COPY … TO PROGRAM`, создавать роли и базы |

Права на таблицы будущих миграций выдаются сами (`ALTER DEFAULT PRIVILEGES`). Пароль роли —
`secrets/sender_app_password`; сменили файл — следующий `migrate` сменит пароль в базе.
Служба `api` на попытку `migrate` ответит, что схему меняет служба `migrate`.

**5. Первая учётная запись.** Пароль спрашивается скрытым вводом дважды. Для сценариев есть
`--password-file путь`, а для имени — `--display-name "Имя"`.

```bash
docker compose run --rm api create-superadmin --email admin@example.com
```

**6. Запуск.** Поднимутся API, база и туннель (`cloudflared` — если в `.env` есть
`COMPOSE_PROFILES=tunnel`). Туннель жив, когда в его журнале есть
`Registered tunnel connection` (`docker compose logs cloudflared`).

```bash
docker compose up -d
```

На самом сервере API слушает только `127.0.0.1:8001`. Проверка:

```bash
curl -s http://127.0.0.1:8001/api/health
```

`/api/health` отвечает, что процесс жив. `/api/ready` дополнительно проверяет базу.

**Без туннеля — свой обратный прокси с TLS.** Уберите из `.env` строки туннеля и выставьте API
наружу через nginx, Caddy или Traefik с сертификатом. Кука обновления — `__Host-sender-refresh` с атрибутами `Secure`, `HttpOnly` и
`SameSite=Strict`, поэтому по голому HTTP браузер её не сохранит. Пример для Caddy:

```
sender.example.com {
    reverse_proxy 127.0.0.1:8001
}
```

Чтобы предел попыток входа считался по адресу клиента, а не прокси, сообщите приложению,
какому прокси верить заголовку `X-Forwarded-For`. В файле `.env` рядом с
`docker-compose.yml` задайте адрес, с которого прокси приходит **в контейнер**. Обычно это
шлюз сети Docker, например `172.18.0.1/32`; можно и список через запятую.

Туннелю приложение верит **только по адресу cloudflared** в сети `edge` (`SENDER_TUNNEL_PROXY_IP`,
по умолчанию `172.31.250.2`; API в ней — `SENDER_TUNNEL_API_IP`, `172.31.250.3`), а не всей
подсети: в подсеть входит и шлюз моста, то есть сам сервер, и любой процесс на нём подделывал бы
адрес клиента. Сменили подсеть `SENDER_TUNNEL_SUBNET` — задайте и оба адреса внутри неё.

```
SENDER_TRUSTED_PROXY_NETWORKS=172.18.0.1/32
```

**Обновление `cloudflared`.** Образ взят как `latest`. Свежую версию подтягивают так:

```bash
docker compose pull cloudflared && docker compose up -d
```

## Панель

Веб-панель открывается в корне сервиса: `https://sender.example.com/`, локально —
http://127.0.0.1:8001. Всё, что описано ниже через `curl`, делается и в ней. Это React + TypeScript
(`EmailSslSender.Web`): образ Docker собирает её сам, отдельной стадией, и отдаёт вместе с API.

| Вкладка | Что там |
|---|---|
| **Рассылка** | Подписки: какой сертификат, кому, какие файлы, когда. Состояние последней отправки; действия — отправить сейчас, изменить, включить / отключить, удалить (на телефоне — «⋯») |
| **Сертификаты** | Сертификаты из последнего опроса Key Manager Plus, со сроками; сортировка по имени или по сроку (заголовок «Действует до»: сначала истекающие ↔ сначала дальние, на телефоне — список «Порядок»; выбор помнит браузер); скачать файл в нужном формате, показать закрытый ключ |
| **Пользователи** | Приглашение, сброс пароля и 2FA, блокировка, удаление |
| **Настройки** | Разделы «Почта» (SMTP, пароль, тестовое письмо, очередь) и «Key Manager» (адрес, ключ API, проверка, опрос) |
| **Безопасность** | Блокировка, сессии, пароли, срок ссылок, окно подтверждения кодом |
| **Профиль** (инициалы справа вверху) | Своё имя, пароль, сессии, выход |

- **Первый вход:** почта и пароль, затем QR-код для приложения-аутентификатора. Дальше вход идёт
  с шестизначным кодом.
- **Свежий код перед важными действиями.** На отказ `403 SECOND_FACTOR_REQUIRED` панель
  открывает окно кода (`POST /api/me/step-up`) и повторяет действие. После кода или входа окно
  длится `auth.step_up_minutes` (по умолчанию 10 минут) и привязано к сессии, а не к человеку.
- **Режим телефона.** Раскладку выбирает режим браузера (`navigator.userAgentData.mobile`, иначе
  строка агента), а не ширина экрана: `html[data-device="mobile"]` — нижние вкладки, списки вместо
  таблиц, окна листом снизу; `desktop` — верхнее меню и таблицы при любой ширине окна.
- **Сессия.** Перезагрузка страницы сессию не теряет. Токен доступа живёт в памяти вкладки, токен
  обновления — в куке `HttpOnly`.
- **Без внешних ресурсов.** Панель работает во внутренней сети без выхода в интернет. Страницы
  закрыты строгой CSP: только свои скрипты и стили, без встраивания во фрейм.

## Первый вход и подключение аутентификатора

Примеры ниже — для скрипта и `curl`: токены приходят в теле ответа (`"use_cookie": false`).
Браузерный клиент передаёт `"use_cookie": true` и получает токен обновления кукой.

```bash
API=http://127.0.0.1:8001
```

**1. Вход паролем.** Аутентификатора ещё нет. Без настроенной почты ответ — `200` с токенами
сессии настройки; с почтой — `401 TWO_FACTOR_REQUIRED` и код письмом (второй шаг ниже), а
сессия настройки выдаётся после него. В `GET /api/me` у неё `"must_enroll_two_factor": true`.

```bash
curl -s -X POST $API/api/auth/login -H 'Content-Type: application/json' -d '{"email":"admin@example.com","password":"ВАШ_ПАРОЛЬ","use_cookie":false}'
```

```bash
TOKEN='значение access_token из ответа'
```

**2. Завести секрет.** Ответ: `{"secret": "...", "uri": "otpauth://totp/..."}`. Значение `uri`
превратите в QR-код (например, `qrencode -t ansiutf8 'otpauth://...'`) или введите `secret`
в приложение вручную. Секрет показывается один раз.

```bash
curl -s -X POST $API/api/me/two-factor/totp/setup -H "Authorization: Bearer $TOKEN"
```

**3. Подтвердить кодом из приложения.** Ответ `204`. С этого момента сессия полноценная.

```bash
curl -s -X POST $API/api/me/two-factor/totp/confirm -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"code":"123456"}'
```

**Следующие входы** проходят в два шага. Вход паролем отвечает
`401 TWO_FACTOR_REQUIRED`. В `details` лежат `challenge` (расписка на 5 минут), `method`
(`totp`) и `available` (`["totp"]`; `email` — только у того, кто аутентификатор ещё не
подключил). С распиской и кодом идут на второй шаг:

```bash
curl -s -X POST $API/api/auth/two-factor -H 'Content-Type: application/json' -d '{"challenge":"РАСПИСКА","code":"123456","use_cookie":false}'
```

Код письмом — только для входа без подключённого аутентификатора (первый вход при
настроенной почте). Владельцу аутентификатора этот запрос отвечает `409`:

```bash
curl -s -X POST $API/api/auth/two-factor/email -H 'Content-Type: application/json' -d '{"challenge":"РАСПИСКА"}'
```

**Обновление пары** выдаёт новый токен доступа и новый токен обновления. Старый токен
обновления после этого недействителен: повторное предъявление считается кражей и закрывает
сессию.

```bash
curl -s -X POST $API/api/auth/refresh -H 'Content-Type: application/json' -d '{"refresh_token":"ТОКЕН_ОБНОВЛЕНИЯ","use_cookie":false}'
```

## Настройка почты по SSL

Почта выключена, пока её не настроят.

**1. Сервер и отправитель.** `mail.smtp_security` задаётся явно и по порту не угадывается:

| Значение | Что делает | Обычный порт |
|---|---|---|
| `tls` | SSL/TLS с первого байта (SMTPS) | 465 |
| `starttls` | Обычное соединение, затем обязательный STARTTLS | 587 |
| `none` | Без шифрования — только ловушка писем или релей в той же сети, **без логина**: пароль по открытому соединению не отправляется | 25, 1025 |

```bash
curl -s -X PATCH $API/api/settings/system -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"values":{"mail.enabled":true,"mail.smtp_host":"smtp.example.com","mail.smtp_port":465,"mail.smtp_security":"tls","mail.smtp_username":"noreply@example.com","mail.from_address":"noreply@example.com","mail.from_name":"EAMS ssl sender","server.public_url":"https://sender.example.com"}}'
```

`server.public_url` — внешний адрес установки. Из него собираются ссылки в письмах
приглашения и сброса пароля.

**2. Пароль SMTP.** Он хранится в базе зашифрованным мастер-ключом и обратно не отдаётся
никогда. Пустая строка снимает пароль. Пароль привязан к серверу, порту, защите и логину,
действующим в момент ввода: после их смены письма не уходят с ошибкой «введите пароль SMTP
заново» — так вошедший не перенаправит пароль на свой сервер. Задавайте сначала настройки,
потом пароль.

```bash
curl -s -X PUT $API/api/mail/password -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"password":"ПАРОЛЬ_SMTP"}'
```

**3. Проверочное письмо** уходит сразу, минуя очередь. Ответ `204` значит, что сервер
письмо принял. При отказе приходит `409 MAIL_SEND_FAILED`, и в `details.reason` лежит ответ
почтового сервера, например `5.7.1 Authentication Required`.

```bash
curl -s -X POST $API/api/mail/test -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"to":"you@example.com","locale":"ru"}'
```

**4. Состояние:** `configured`, `password_set`, сколько писем ждёт (`pending`), сколько
не ушло (`failed`) и последняя ошибка (`last_error`).

```bash
curl -s $API/api/mail -H "Authorization: Bearer $TOKEN"
```

**Как работает очередь.** Письма из кода (приглашения, сброс, коды входа) кладутся в таблицу
`mail_outbox` в той же транзакции, что и действие. Если действие откатилось, письма нет.
Насос в фоне забирает строки (`FOR UPDATE SKIP LOCKED`, поэтому безопасно и при нескольких
экземплярах) и повторяет попытки до `mail.max_attempts`. Тела писем в таблице зашифрованы,
отправленные убираются уборкой. Предел `mail.rate_per_hour` считается на пару «адрес + вид
письма» и защищает чужой ящик от форм сброса и кодов.

Каждое письмо уходит двумя частями — текстом и HTML (`multipart/alternative`; с вложениями — внутри
`multipart/mixed`). HTML собирает модуль почты из того же текста шаблона: абзацы, таблицы, рамка с
приветствием и подписью; всё экранировано, ссылок и внешних ресурсов нет. HTML-часть запечатана в
очереди тем же ключом данных, что и текст (колонка `mail_outbox.html_body`).

**Сертификат сервера проверяется полностью, включая отзыв (CRL/OCSP).** У публичных
провайдеров это работает само. Если SMTP-сервер стоит во внутренней сети с собственным
удостоверяющим центром:

- в сертификате должна быть точка распространения CRL, доступная из контейнера, иначе
  отказ будет «unable to get certificate CRL»;
- корневой сертификат передайте контейнеру: смонтируйте файл и задайте
  `SSL_CERT_FILE=/путь/ca-bundle.pem` в `environment` сервиса `api`.

Отключать проверку не нужно и нельзя: пароль SMTP уехал бы тому, кто встал посередине.

## Сертификаты из Key Manager Plus

Сервис опрашивает ManageEngine Key Manager Plus (проверено по документации REST API для 7.1.1,
build 7110) и рассылает файлы SSL-сертификатов по **подпискам**: какие сертификаты (Common Name —
один или несколько, до 50), кому, в каких файлах и когда.

**Когда уходит письмо.**

- **Сертификат обновился** (`on_change`). Вебхуков и истории у API Key Manager Plus нет, поэтому
  обновление определяется опросом раз в `keymanager.poll_minutes`. Если у Common Name появился новый
  серийный номер (продление, в том числе автоматическое, или перевыпуск), уходит **только этот
  сертификат**, а не все в подписке. Если в Key Manager Plus лежат и старый, и новый, берётся
  замеченный позже, даже если срок у него тот же или короче. Среди замеченных одновременно
  выигрывает тот, что действует дольше.
- **По расписанию** (`interval_days`): раз в N дней уходят **все** сертификаты подписки. Срок
  считается от последней полной отправки (`last_full_sent_at`); частичная «при обновлении» его не
  сдвигает.
- **Сразу после заведения подписки** и после добавления сертификата в подписку: опрос будится, и
  ещё не отправленные сертификаты уходят в течение секунд.
- **Вручную** — `POST /api/certificate-subscriptions/{id}/send`, кнопка «Отправить сейчас»: все
  сертификаты подписки.

**Период и время отправки** (с 2.4) ограничивают только опрос; ручная отправка шлёт всегда.

- **Период** (`active_from`, `active_until`, оба дня включительно, можно задать один): до первого дня и
  после последнего опрос подписку не шлёт и не трогает — ни выгрузки, ни ошибок в `last_error`. В
  первый день уходит всё, что ещё не отправлено: при обновлении — неотправленные сертификаты, по
  расписанию — все.
- **Время отправки** (`send_time`) — «в это время», а не «не раньше». Опрос разбирает каждое время
  отправки один раз: шлёт то, что пора, и до следующего дня молчит. Обновление, замеченное в 10:00 при
  времени 09:00, уходит завтра в 09:00. Пропущенное время — сервис стоял, Key Manager Plus не отвечал —
  догоняется первым удачным опросом после него. «Раз в N дней» со временем отправки считается днями
  календаря: раз в день — каждый день в 09:00.
- После заведения подписки, смены периода, времени или пояса и после включения подписки первое
  письмо уходит в ближайшее время отправки: прошедшее сегодня не догоняется.
- Автоповтор (не дошло ни одно письмо) время отправки не ждёт, а период соблюдает.
- Дни и время — по часовому поясу подписки (`time_zone`, IANA, например `Europe/Kyiv`; панель берёт
  его из браузера), с переходом на летнее время. Время, которого в этот день нет (часы переведены
  вперёд), наступает в первую минуту после перевода.

Подписка обязана иметь **хотя бы один способ отправки** — `on_change` или `interval_days`; без них
сервис её не сохранит (`400`, поле `on_change`): такая подписка молча ничего не слала бы. Проверка
срабатывает, когда задают или меняют способ; подписку 2.0 без способа можно править (например,
убрать получателя), не выбирая его.

Сертификат подписки, которого нет в Key Manager Plus или который не выгрузился (например, у него в
Key Manager Plus нет закрытого ключа), не мешает остальным: они уходят, а в `last_error` подписки —
«Сертификата … нет в Key Manager Plus» или «… не выгрузился: причина» и «— отправлены остальные».
Не выгрузившийся сертификат не отмечается отправленным: «при обновлении» попробует его снова на
следующем опросе. Не выгрузился ни один — ничего не уходит, причина — в `last_error`.

**Защита от отката.** Key Manager Plus может снова внести старый сертификат — например, сканирование
нашло его на ещё не обновлённом сервере, — и он окажется «замеченным позже всех». Сервис сравнивает
**дату выпуска** (`NotBefore` из файла сертификата) с датой уже отправленного: выпущенный раньше
сам не уходит. Если отправленный ещё есть в Key Manager Plus, текущим остаётся он; если нет — опрос
ничего не шлёт и пишет в `last_error` «…только выпуск старее отправленного…», а «Отправить сейчас»
отправит его как решение администратора. Срок для этого не годится: сертификат, продлённый досрочно
под новые предельные сроки, истекает раньше прежнего. У подписок, отправленных до 2.2, защита
включается с их следующей отправкой.

**Автоповтор, если не дошло ни одно письмо.** Если почта лежала дольше всех попыток очереди и не дошло
**ни одно** письмо отправки, сервис снимает её отметки и отправляет заново тем же опросом — не больше
трёх раз подряд, дальше только кнопкой. Если письмо не дошло лишь части получателей, повтора нет
(остальным пришли бы дубли): причина — в `last_error`, отправить повторно — кнопкой.

**Почта без шифрования.** Закрытый ключ (`KEY`, `PKCS`, `JKS`) и его пароль по SMTP с
`mail.smtp_security = none` не отправляются: подписка получает отказ с объяснением. Сертификаты без
ключа (`PEM`, `CRT`, `CER`, `DER`, `P7B`) — открытые данные и уходят.

Файлы уходят **одним архивом на письмо** (Outlook блокирует вложения `.crt`, `.cer` и `.der`): один
сертификат — `<Common Name>.zip` с файлами в корне (звёздочка — `wildcard`), несколько —
`ssl-certificates.zip` с папкой на каждый сертификат. Пароль ключа (`include_passphrase`) лежит в
папке сертификата файлом `passphrase.txt`. Письмо: приветствие, **таблица сертификатов** — как в
уведомлении Key Manager Plus, но без серийного номера и отпечатка, — что в архиве, подпись «EAMS ssl
sender». Колонки на языке письма:

| `ru` | `uk` | `en` |
|---|---|---|
| Сертификат | Сертифікат | Certificate |
| Форматы | Формати | Formats |
| Действует до | Дійсний до | Valid until |
| Осталось дней | Залишилось днів | Days to expire |

Письмо уходит двумя частями: HTML с настоящей таблицей и простой текст для клиентов без HTML — в
нём таблица строкой на сертификат, ячейки через « · ». В HTML-части нет ссылок, картинок и внешних
ресурсов. Тема — «SSL-сертификат имя» или «SSL-сертификаты a, b, c и ещё N».

> ⚠ **Письмо несёт закрытый ключ** (тип `KEY`, а также `PKCS` и `JKS`). Любой, кто прочтёт ящик
> получателя или пересланное письмо, получит ключ. В очереди вложения лежат запечатанными и
> стираются, как только письмо ушло или исчерпало попытки. Шлите ключ только тем, кому он
> действительно нужен.

**1. Ключ API.** В Key Manager Plus откройте **Settings → General Settings → API Key** и нажмите
**Generate**. Ключ привязан к хосту, на котором его создали. У нас он хранится запечатанным
мастер-ключом и обратно не отдаётся. Пустая строка снимает ключ. Ключ привязан к
`keymanager.base_url`, действующему в момент ввода: задайте сначала адрес, потом ключ; после смены
адреса ключ вводится заново.

```bash
curl -s -X PUT $API/api/keymanager/api-key -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"api_key":"3E014D78-E603-413A-AC24-6392F0001283"}'
```

**2. Адрес и проверка TLS.** Нужен адрес `https://` с портом (по умолчанию у Key Manager Plus —
6565). Ключ едет в заголовке `AUTHTOKEN`, поэтому открытый HTTP отвергается. Сертификат Key Manager
Plus проверяется полностью: цепочка до удостоверяющего центра, имя из адреса и отзыв. Значит, имя в
адресе — то, на которое выдан сертификат (не IP), а контейнеру нужен доступ к OCSP/CRL центра.

```bash
curl -s -X PATCH $API/api/settings/system -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"values":{"keymanager.base_url":"https://kmp.example.local:6565"}}'
```

**Самоподписанный сертификат не принимается** (с 2.5 настройки `keymanager.server_sha256` и
закрепления отпечатка нет): у Key Manager Plus должен быть сертификат удостоверяющего центра.
Сертификат своего (корпоративного) центра принимается, если его корневой сертификат передан
контейнеру через `SSL_CERT_FILE`, как для SMTP.

**3. Проверка связи** работает и до включения интеграции. Ответ — число сертификатов, которые
видит Key Manager Plus. При отказе приходит `409 KEYMANAGER_UNAVAILABLE`, а в `details.reason`
лежит причина: ключ не принят, TLS не согласован, сервер недоступен.

```bash
curl -s -X POST $API/api/keymanager/test -H "Authorization: Bearer $TOKEN"
```

**4. Включить опрос:**

```bash
curl -s -X PATCH $API/api/settings/system -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"values":{"keymanager.enabled":true,"keymanager.poll_minutes":15}}'
```

**5. Подписка.** Обязательны `common_names` (или один `common_name`) и `recipients`. Остальные поля:

| Поле | По умолчанию | Что задаёт |
|---|---|---|
| `common_names` | — | Сертификаты: от 1 до 50 Common Name; пробелы, пустые и повторы (без учёта регистра) отбрасываются. Один сертификат можно передать и полем `common_name` — но не оба поля сразу |
| `formats` | `["PEM","KEY"]` | Типы файлов из Key Manager Plus: `CER`, `CRT`, `DER`, `P7B`, `PKCS`, `JKS`, `PEM`, `KEY` |
| `on_change` | `true` | Слать обновлённый сертификат, когда у него новый серийный номер |
| `interval_days` | нет | Слать все сертификаты раз в N дней (1–365). В `PATCH` значение `0` снимает расписание. Хотя бы одно из `on_change` и `interval_days` обязательно |
| `include_passphrase` | `false` | Приложить пароль закрытого ключа из Key Manager Plus файлом `passphrase.txt` |
| `locale` | `ru` | Язык письма: `ru`, `uk`, `en` |
| `enabled` | `true` | Отключённую подписку опрос не шлёт; вручную её отправить можно |
| `description` | нет | Описание для администраторов, до 500 знаков: для кого и зачем рассылка. Видно только в панели и API, в письма не уходит; в журнал пишется только его длина. Пустая строка в `PATCH` снимает описание |
| `active_from`, `active_until` | нет | Период, в который опрос шлёт подписку сам: дни `ГГГГ-ММ-ДД`, оба включительно, можно задать один; последний не раньше первого. Пустая строка снимает. Нужен `time_zone` |
| `send_time` | нет | Время отправки `ЧЧ:ММ` (секунды отбрасываются): письма опроса уходят в это время, замеченное позже — на следующий день. Пустая строка снимает — тогда сразу. Нужен `time_zone` |
| `time_zone` | нет | Часовой пояс IANA (`Europe/Kyiv`, `UTC`) для периода и времени отправки. Без них не хранится |

```bash
curl -s -X POST $API/api/certificate-subscriptions -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"common_names":["*.example.com","vpn.example.com"],"recipients":["admin1@example.com","admin2@example.com"],"formats":["PEM","KEY"],"interval_days":30}'
```

Каждый адрес получает своё письмо. В ответе подписки `sent_serials` — какой серийный номер ушёл
последним по каждому Common Name, `last_sent_at` — последняя отправка, `last_full_sent_at` — последняя
отправка всех сертификатов, `period` — где подписка относительно периода: `before` (первый день не
наступил), `active`, `after` (последний день прошёл) или `null` (периода нет). Поле `delivery` показывает судьбу последней отправки:
- `queued` — письма в очереди;
- `sent` — сервер их принял;
- `failed` — не ушли, причина в `last_error`;
- `none` — подписка ещё не отправлялась.

Если письмо исчерпало попытки, подписка показывает адрес и ответ почтового сервера. **Повторно она
не отправляется сама:** иначе при одном несуществующем ящике остальные получатели получали бы
дубли каждый час. Устраните причину и нажмите «Отправить».

Состояние опроса — `GET /api/keymanager`. Сертификаты, которые видел опрос, и когда каждый замечен
впервые — `GET /api/keymanager/certificates`.

Почта проверяется до выгрузки: пока она не настроена, закрытые ключи из Key Manager Plus не
выгружаются вовсе. Удаление подписки, удаление получателя, убранный из подписки сертификат или
формат (например, `KEY`), снятый `include_passphrase` и отключение подписки отменяют её
неотправленные письма — закрытый ключ не уходит после того, как право на него отняли. Кроме удаления
получателя, отменённые письма несли и остальное: подписка забывает отправленное, и оставшееся уйдёт
заново ближайшим опросом уже по новым правилам (отключённая — после включения). Письмо с вложениями, не ушедшее за 24 часа, теряет вложения и считается
неотправленным — после починки почты отправьте подписку заново.

Какие методы REST API Key Manager Plus вызывает сервис, с какими параметрами и что берёт из
ответа — [KEYMANAGER-API.md](KEYMANAGER-API.md).

**Что сверить на своём Key Manager Plus.** Документация не описывает, в каком виде
`getCertificate` отдаёт файлы. Клиент принимает только то, что похоже на файл сертификата или
ключа: PEM, DER/PKCS, JKS или ZIP. JSON или HTML вместо файла считаются отказом. После первой
ручной отправки откройте вложения и убедитесь, что это то, что нужно. Если нет, клиент
дописывается по тексту `last_error`.

## Учётные записи

**Пригласить.** Если почта настроена, приглашение уходит письмом и `invitation_token` в
ответе пуст. Если нет — ссылка возвращается в ответе один раз, и её передают человеку
самостоятельно: `https://sender.example.com/activate#token=ЗНАЧЕНИЕ`. Ссылка живёт
`auth.invitation_ttl_minutes`. На странице `/activate` человек задаёт пароль. Токен лежит
во фрагменте `#`, на сервер в адресе не уходит и сразу стирается из адресной строки.

```bash
curl -s -X POST $API/api/users -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"email":"colleague@example.com","display_name":"Коллега"}'
```

Приглашённый при первом входе тоже получает сессию настройки и подключает свой
аутентификатор.

**Список** (курсорная выдача: `?limit=50&after=...`, значение берётся из `next_cursor` ответа):

```bash
curl -s "$API/api/users?limit=50" -H "Authorization: Bearer $TOKEN"
```

**Остальное** — по `id` из списка:

| Действие | Запрос |
|---|---|
| Изменить имя или потребовать смену пароля | `PATCH /api/users/{id}` с `{"display_name": "...", "must_change_password": true}` |
| Отключить / включить | `POST /api/users/{id}/disable`, `POST /api/users/{id}/enable` |
| Удалить | `DELETE /api/users/{id}` |
| Снять блокировку после неудачных входов | `POST /api/users/{id}/unlock` |
| Снять второй фактор (потерян телефон) | `DELETE /api/users/{id}/two-factor` |
| Закрыть все сессии, не отключая | `DELETE /api/users/{id}/sessions` |
| Ссылка сброса пароля | `POST /api/users/{id}/reset-password` — письмом или в ответе, как приглашение |
| Повторить приглашение | `POST /api/users/{id}/invite` — прежняя ссылка гасится |

**«Забыл пароль»** — `POST /api/password-reset/request` с `{"email": "..."}`. Ответ всегда
`202`, есть адрес или нет, а ссылка уходит **только письмом**. Без настроенной почты этот путь
ничего не делает. Тогда ссылку выдаёт другой администратор или консольная команда
`set-superadmin-password`.

## Справочник API

Все тела — JSON. Токен передаётся заголовком `Authorization: Bearer ...`.
Пометки: **П** — публичный, **Н** — открыт и в сессии настройки, **Ф** — нужен свежий код
(подтверждён в этой сессии за последние `auth.step_up_minutes` минут), иначе
`403 SECOND_FACTOR_REQUIRED`. С версии 2.0 код требуют и правка любой настройки, и правка учётной
записи, и проверочное письмо, и смена своего пароля (правила модулей EAMS).

| POST | `/api/auth/two-factor/email` | П | Прислать код входа письмом: `challenge` |
| POST | `/api/auth/refresh` | П | Новая пара: `refresh_token` (или кука), `use_cookie` |
| POST | `/api/auth/logout` | | Закрыть текущую сессию |
| GET | `/api/auth/password-policy` | Н | Требования к паролю |
| GET | `/api/me` | Н | Кто я: `id`, `email`, `must_change_password`, `must_enroll_two_factor`, `step_up_until` (до какого времени код не спросят; `null` — спросят) |
| PATCH | `/api/me` | | Своё имя: `display_name` |

| POST | `/api/users/{id}/reset-password` | Ф | Выдать ссылку сброса |
| POST | `/api/users/{id}/invite` | Ф | Повторить приглашение |

нет, но документ можно выгрузить в файл без сервера и базы. Скрипт подставляет одноразовый
ключ и пишет `openapi.json` в корень, по нему генерируют клиентов.

```bash
./scripts/export-openapi.sh
```

**Ошибки** приходят одним конвертом:
`{"code": "...", "message": "...", "details": {...}, "request_id": "..."}`.
Клиенту нужно разбирать `code`, а не текст сообщения:

| Код | HTTP | Что значит |
|---|---|---|
| `UNAUTHENTICATED` | 401 | Нет токена или он недействителен |
| `TOKEN_EXPIRED` | 401 | Срок токена доступа вышел — обновите пару |
| `SESSION_REVOKED` | 401 | Сессия закрыта: выход, отзыв, кража — войдите заново |
| `INVALID_CREDENTIALS` | 401 | Неверный адрес или пароль (одинаково для обоих случаев) |
| `TWO_FACTOR_REQUIRED` | 401 | Пароль принят, нужен код: `details.challenge` |
| `TWO_FACTOR_INVALID` | 401 | Код не подошёл |
| `TWO_FACTOR_ENROLLMENT_REQUIRED` | 403 | Сессия настройки: сначала подключите аутентификатор |
| `PASSWORD_CHANGE_REQUIRED` | 403 | Сначала смените пароль |
| `SECOND_FACTOR_REQUIRED` | 403 | Нужен свежий код: `POST /api/me/step-up`, затем повторить; `details.window_minutes` |
| `LAST_SUPERADMIN` | 409 | Это последняя активная учётная запись |
| `PASSWORD_POLICY_VIOLATION` | 400 | Пароль не по правилам, подробности в `details` |
| `MAIL_NOT_CONFIGURED` | 409 | Почта не настроена |
| `MAIL_SEND_FAILED` | 409 | Почтовый сервер отказал: `details.reason` |
| `KEYMANAGER_NOT_CONFIGURED` | 409 | Не заданы адрес Key Manager Plus или ключ API |
| `KEYMANAGER_UNAVAILABLE` | 409 | Key Manager Plus не ответил или отказал: `details.reason` |
| `KEYMANAGER_CERTIFICATE_NOT_FOUND` | 409 / 404 | Ни одного сертификата подписки в Key Manager Plus нет; 404 — у выгрузки, когда пары «имя + серийный» нет в последнем снимке |
| `DELIVERY_IN_PROGRESS` | 409 | Эту подписку прямо сейчас отправляет опрос |
| `RATE_LIMITED` | 429 | Слишком часто |
| `VALIDATION_ERROR` | 400 | Тело запроса не прошло проверку |

Полный список — общие коды ядра в `modules/core/src/Modules.Core/Errors/ErrorCodes.cs`, коды модулей —
в их `Contracts/*ErrorCodes.cs` (учётные записи, почта) и в
[KeyManagerErrorCodes.cs](../EmailSslSender.Modules.KeyManager/Contracts/KeyManagerErrorCodes.cs).

## Настройки

Настройки хранятся в базе и меняются через `PATCH /api/settings/system`, без перезапуска.
`GET` возвращает все настройки с умолчаниями, границами и допустимыми значениями.
`"reset": ["ключ"]` возвращает настройке умолчание.

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `mail.enabled` | `false` | Слать ли почту вообще |
| `mail.smtp_host` | — | Сервер SMTP |
| `mail.smtp_port` | `587` | Порт |
| `mail.smtp_security` | `starttls` | `tls`, `starttls` или `none` |
| `mail.smtp_username` | — | Пользователь SMTP; пусто — без авторизации |
| `mail.from_address` | — | Адрес в `From`; без него почта считается ненастроенной |
| `mail.from_name` | `EAMS ssl sender` | Имя в `From` |
| `mail.rate_per_hour` | `5` | Писем в час на адрес и вид |
| `mail.max_attempts` | `5` | Попыток доставки |
| `server.public_url` | `https://sender.example.com` | Внешний адрес для ссылок в письмах |
| `keymanager.enabled` | `false` | Опрашивать ли Key Manager Plus и рассылать ли сертификаты |
| `keymanager.base_url` | — | Адрес Key Manager Plus, только `https://`, например `https://kmp.example.local:6565` |
| `keymanager.poll_minutes` | `15` | Как часто опрашивать (1–1440 минут) |
| `auth.two_factor_challenge_minutes` | `5` | Сколько живёт расписка между паролем и кодом |
| `auth.step_up_minutes` | `10` | Сколько после кода (или входа с кодом) важные действия его не спрашивают (1–120 минут) |
| `auth.password_min_length` и `auth.password_require_*` | — | Политика паролей |
| `auth.lockout_threshold`, `auth.lockout_minutes` | — | Блокировка после неудачных входов |
| `auth.access_ttl_minutes` | — | Срок токена доступа |
| `auth.session_idle_minutes`, `auth.session_absolute_hours` | — | Простой и предельный срок сессии |
| `auth.refresh_grace_seconds` | — | Окно, в котором повтор обновления не считается кражей (две вкладки) |
| `auth.session_retention_days`, `identity.link_retention_days` | — | Сколько хранить закрытые сессии и погашенные ссылки |
| `auth.invitation_ttl_minutes` | — | Срок ссылок приглашения и сброса |
| `ui.locale` | `ru` | Язык писем: `ru`, `uk` или `en` |

Прочерк значит, что умолчание смотрите в `GET /api/settings/system`.

Пределы частоты на входе лежат в `appsettings.json`, раздел `RateLimits`, и меняются
перезапуском.

## Своё письмо из кода

Шаблон объявляет тот, кто шлёт. Модуль почты при этом не правится.

**1. Шаблоны.** Нужны все три языка: при старте справочник проверяет, что у каждого вида
есть `ru`, `uk` и `en`. Подстановки пишутся как `{имя}`. Приветствие и подпись с именем сервиса
добавляет рамка модуля почты — в шаблоне их не пишут.

⚠ Модуль почты **вырезает переводы строк и невидимые знаки из подставляемых значений** (иначе чужое
значение подкладывало бы абзац в тело или заголовок в тему). Список — строками шаблона, а не одним
значением; образец — `CertificateMail` модуля Key Manager (вид на число файлов).

```csharp
using Modules.Core.Contracts.Mail;

internal sealed class ReportMailTemplates : IMailTemplateProvider
{
    public const string ReportReady = "report_ready";

    public IReadOnlyList<MailTemplate> Templates { get; } =
    [
        new(ReportReady, MailLocales.Ru, "Отчёт готов", "Отчёт «{name}» готов:\n{link}"),
        new(ReportReady, MailLocales.Uk, "Звіт готовий", "Звіт «{name}» готовий:\n{link}"),
        new(ReportReady, MailLocales.En, "Report ready", "Report \"{name}\" is ready:\n{link}"),
    ];
}
```

**2. Регистрация** — в `Program.cs` или в своём модуле:

```csharp
builder.Services.AddSingleton<IMailTemplateProvider, ReportMailTemplates>();
```

**3. Отправка.** `EnqueueAsync` не сохраняет сам: письмо уезжает в базу с вашим
`SaveChangesAsync`, в одной транзакции с вашим действием. Метод не бросает исключений, а
возвращает результат. Токен отмены — именованным аргументом: перед ним стоит необязательный срок
жизни письма `expiresAt`.

```csharp
public sealed class ReportService(IMailQueue mail, AppDbContext db)
{
    public async Task NotifyAsync(string to, string name, string link, CancellationToken ct)
    {
        var result = await mail.EnqueueAsync(
            to,
            ReportMailTemplates.ReportReady,
            MailLocales.Ru,
            new Dictionary<string, string> { ["name"] = name, ["link"] = link },
            cancellationToken: ct);

        // Queued — уйдёт насосом; NotConfigured — почта не настроена; RateLimited — предел адреса
        await db.SaveChangesAsync(ct);
    }
}
```

`IMailQueue.CanSendAsync()` заранее отвечает, настроена ли почта. Вложения, номер письма, его
состояние и отмена — перегрузка `EnqueueAsync(..., attachments, ...)`, `StatusAsync`, `CancelAsync`.

## Свой эндпоинт

Контроллер ASP.NET Core в своём модуле по образцу `EmailSslSender.Modules.KeyManager`
(`mvc.AddModule(сборка, переключатели)` подключает внутренние контроллеры модуля). Действие
**обязано объявить доступ**, иначе фильтр прав отвечает `403` всем:

- `[AuthenticatedEndpoint("причина")]` — нужен вход (ролей в проекте нет, этого достаточно);
- `[RequireRecentSecondFactor]` — вдобавок свежий код второго фактора;
- `[PublicEndpoint("причина")]` — открыто без входа; причина обязательна.

```csharp
using Microsoft.AspNetCore.Mvc;
using Modules.Core.Contracts.Audit;
using Modules.Core.Contracts.Authz;

[ApiController]
[AuthenticatedEndpoint("ролей в проекте нет: каждая учётная запись — администратор")]
[Route("api/reports")]
internal sealed class ReportsController(ICurrentUser me, IAuditWriter audit) : ControllerBase
{
    [HttpGet]
    public object List() => new { owner = me.Id };

    [HttpDelete("{id:guid}")]
    [RequireRecentSecondFactor]
    public IActionResult Delete(Guid id)
    {
        audit.Write(new AuditEntry(ReportActions.Deleted,
            ActorId: me.Id, ResourceType: "report", ResourceId: id));
        return NoContent();
    }
}
```

- `ICurrentUser.Id` — кто вошёл, `SessionId` — его сессия, `StepUpAt` — когда подтверждён код.
- События журнала модуль объявляет (`IAuditActionProvider`, образец — `KeyManagerAuditActions`);
  `IAuditWriter` пишет строку `audit ...` в журнал приложения.
- Тест `ЗакрытоПоУмолчанию` сам проверит, что новое непубличное действие отвечает невошедшему `401`.

## Обслуживание

**Вернуть доступ одной командой** (забыт пароль, потерян телефон): новый пароль (скрытый ввод
дважды или `--password-file`), снятие второго фактора, снятие блокировки, закрытие всех сессий
и гашение ссылок — одной транзакцией. Отключённую учётную запись команда не включает и говорит
об этом.

```bash
./scripts/reset-access.sh admin@example.com
```

то же самое без скрипта: `docker compose run --rm api reset-access --email admin@example.com`.

**По отдельности.** Только пароль:

```bash
docker compose run --rm api set-superadmin-password --email admin@example.com
```

Только второй фактор — снимает его, закрывает сессии, и следующий вход начнётся с подключения:

```bash
docker compose run --rm api reset-superadmin-2fa --email admin@example.com
```

**Ротация мастер-ключа.**

1. Допишите в `secrets/sender_master_kek` строку `2:` с новым ключом, сгенерированным
   командой `openssl rand -base64 32`. Первая строка без номера — это версия 1. Действующей
   становится наибольшая версия.
2. Перезапустите API (`docker compose up -d`).
3. Переложите обёртки всех секретов под новую версию:

   ```bash
   docker compose run --rm api rewrap-keys
   ```

4. Когда команда сообщит, что переложено всё (включая неотправленные письма `mail_outbox`),
   старую строку можно убрать. Учтите: копии
   базы, снятые раньше, открываются только старым ключом.

**Резервные копии.** Снимайте `pg_dump` базы `sender` и **отдельно** храните мастер-ключ.
Папка `backups/` в git не попадает.

```bash
mkdir -p backups && docker compose exec -T postgres pg_dump -U sender sender > backups/sender.sql
```

**Журнал действий** — таблица `audit_log` в базе (модуль audit). События входа, отзыва сессий,
изменений учётных записей, настроек и подписок, выгрузки сертификатов и показа закрытых ключей,
отказы прав и обходы суперпользователя (каждый администратор — суперпользователь; повторные чтения в
одной сессии сворачиваются). Журнал **только дописывается**: `UPDATE`, `DELETE` и `TRUNCATE`
отвергает сама база, даже владельцу схемы; каждая строка сцеплена с предыдущей хешем SHA-256.
Хранится всегда — срок хранения выключен. Секреты и адреса получателей туда не попадают.

Читать — `GET /api/audit` (фильтры `action`, `actor_id`, `resource_id`, `since`, `until`, курсор),
справочник событий — `GET /api/audit/actions`, выгрузка CSV или JSON — `POST /api/audit/export`.

Проверить, что журнал не переписан задним числом:

```bash
docker compose run --rm api verify-audit-chain
```

Код 0 — цел, 2 — разрыв. Раз в сутки голова цепочки пишется в лог строкой `audit_chain_anchor`;
переписанную целиком цепочку видно сверкой с этими строками — храните их вне сервера (сбор логов).

Каждое событие по-прежнему пишется и строкой `audit <действие> <итог> actor=... resource=...` в лог
приложения (JSON, Serilog): значения изменений (было → стало) — только у настроек и Key Manager Plus,
у прочих — имена полей; из решений о праве — только отказы (`authz.denied`).

```bash
docker compose logs api | grep '"audit '
```

**Обновление:** `docker compose pull api` (или `docker compose build --pull` из исходников), затем
`docker compose run --rm migrate`, затем `docker compose up -d`. Переход с 1.x на 2.0 — README,
«Обновление до 2.0»: копия базы обязательна, все входят заново.

**Сброс доступа из переменных (Portainer)** — `SENDER_RESET_ACCESS_EMAIL` и
`SENDER_RESET_ACCESS_PASSWORD` — применяется **один раз** на пару «адрес + пароль»: следующие
обновления стека с теми же переменными его не повторяют (в базе — HMAC-отметка, не пароль). Сбросить
снова — задайте другой пароль. Переменные всё равно уберите после входа: пароль в переменных стека
виден в Portainer и `docker inspect`.

## Что учесть

- **Порядок модулей в `Program.cs` несущий.** Движок прав регистрируется до модуля токенов (тот
  оборачивает последнюю регистрацию), набор миграций проекта — после модулей. Причины записаны
  комментариями у каждого звена.
- **Поведение модулей EAMS меняется только новой версией модуля.** Правка в `modules/<имя>` руками
  уйдёт при следующем обновлении подмодуля и разойдётся с репозиторием модуля; модуль дорабатывается в
  EAMS, выпускается меткой и закрепляется здесь заново (раздел «Модули EAMS подмодулями»).
- **Код письмом не заменяет аутентификатор** (ревью безопасности 2026-10-20) — опция
  `AuthenticatorExcludesEmailCode` модуля учётных записей. Выключить её — значит сделать почтовый
  ящик единственным ключом ко входу: сброс пароля и код приходят туда же.
- **Свежий код — на важных действиях** (`[RequireRecentSecondFactor]`, окно — настройка
  `auth.step_up_minutes`). Новое опасное действие помечается атрибутом. Отметка свежести — на токене
  сессии (`StepUpAt`), а не на человеке: код в одной вкладке не открывает другие.
- **Комментарии в коде** ссылаются на этапы, решения и правила EAMS: «решение 0061»,
  «правило 14», «вскрытие 43». Документы EAMS сюда не перенесены. Ссылки оставлены как
  история причин, и смысл каждого комментария понятен без них.
- **Строки разделения ключей** входят в зашифрованные данные. У модулей EAMS — `eams:secret:v1`,
  `eams:system-secret:…`, `eams:mail-body` и подобные; у модуля Key Manager — `sender:keymanager:api-key`.
  После установки их менять нельзя: прежние секреты перестанут открываться (переход 1.x → 2.0
  перекладывает их один раз командой `migrate`).
