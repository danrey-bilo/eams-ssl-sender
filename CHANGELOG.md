## 2.5.0 — 2026-10-28

**Только сертификат удостоверяющего центра у Key Manager Plus, сортировка сертификатов по сроку,
руководство пользователя.** Обновление — обычное: копия базы, новый образ, `migrate`, `up -d`.

### Key Manager Plus

- **Закрепление отпечатка для самоподписанного сертификата убрано полностью** (решение владельца:
  у Key Manager Plus сертификат удостоверяющего центра). Сертификат сервера проверяется только
  цепочкой, именем из адреса и отзывом; самоподписанный не принимается, отключить проверку нечем.
  Поле «Отпечаток SHA-256» ушло из панели, настройка `keymanager.server_sha256` — из сервиса и API.
  Сертификат своего (корпоративного) центра по-прежнему принимается через `SSL_CERT_FILE`.
- Ключ API привязан теперь только к адресу. **Ключ, введённый без отпечатка, открывается как был** —
  вводить его заново не нужно. Если отпечаток был закреплён, после обновления опрос откажет с «Введите
  ключ API заново»: введите ключ в **Настройки → Key Manager**.
- Сбой TLS объясняется словами: «нужен сертификат удостоверяющего центра на имя из адреса,
  самоподписанный не принимается».
- Миграция Key Manager `DropServerPin` убирает строку `keymanager.server_sha256` из `system_settings`.
  Подписки, отправленное и ключ API не меняются.

### Сертификаты

- **Сортировка по сроку**: щелчок по заголовку **Действует до** — сначала истекающие, повторный —
  сначала дальние; щелчок по **Сертификат** — снова по имени. Стрелка у заголовка показывает
  направление. На телефоне — список «Порядок» над сертификатами. Выбор помнит браузер.

### Документация

- **Руководство пользователя** в Word — `docs/Инструкция пользователя EAMS ssl sender.docx`: вход,
  подключение почты и Key Manager Plus, сертификаты, настройка рассылки, что получает получатель,
  форматы файлов (PEM, CRT, CER, DER, P7B, PFX, JKS, KEY, `passphrase.txt`), что выбрать для nginx, IIS,
  Java, как проверить файлы, пользователи, безопасность, работа с телефона, частые вопросы. Снимки — из
  панели 2.5.0 на учебном стенде.
- README, REFERENCE, KEYMANAGER-API — без отпечатка, с сортировкой.

### Проверено

- Тесты: 324. Интеграционные TLS-тесты — на настоящем соединении: самоподписанный сертификат
  отвергается без единого запроса, сертификат доверенного корня проходит, ключ не уходит на сменённый
  адрес даже с годным сертификатом; ключ, привязанный при отпечатке, требует ввода заново.

## 2.4.0 — 2026-10-28

**Период и время отправки подписки.** Обновление — обычное: копия базы, новый образ, `migrate`,
`up -d`. Прежние подписки шлют как раньше.

### Рассылка

- **Время отправки** — поле в окне подписки, например 09:00: письма опроса уходят в это время.
  Обновление, замеченное позже, уходит на следующий день в то же время; пропущенное время (сервис
  стоял) догоняется первым опросом после него. «Раз в N дней» со временем считается днями: раз в день
  — каждый день в 09:00. Пустое время — сразу, как прежде.
- **Запланированный старт и окончание** — галочка и два дня: с какого и по какой день (включительно)
  опрос шлёт подписку. До первого дня и после последнего не шлёт; в первый день уходит всё
  неотправленное. Можно задать только начало или только окончание. В списке — период и «ещё не
  началась» / «окончена»; окончившаяся подписка приглушена, как выключенная.
- Дни и время — по часовому поясу браузера, в котором подписку завели (`time_zone`, IANA), с переходом
  на летнее время. **Отправить сейчас** работает всегда — и вне периода, и не в своё время.
- После заведения подписки и смены периода или времени первое письмо уходит в ближайшее время
  отправки. Автоповтор (не дошло ни одно письмо) время отправки не ждёт.
- API: поля `active_from`, `active_until`, `send_time`, `time_zone` у `POST`/`PATCH
  /api/certificate-subscriptions` и в ответах, там же `period` (`before` / `active` / `after`). Пустая
  строка снимает.
- Миграция Key Manager `SubscriptionSchedule`: колонки `active_from`, `active_until`, `send_time`,
  `time_zone` и служебная `last_slot_at` у `certificate_subscriptions`, все необязательные, с
  проверками в базе. Подписки и отправленное не меняются, повторной рассылки нет.

### Проверено

- Тесты: 7 новых в модуле (период до начала и после конца, ручная вне периода, время отправки держит
  письмо до своего часа, пропущенное время догоняется один раз, «раз в день» в своё время, пояс
  подписки, автоповтор не ждёт) и 6 в API (хранение и снятие полей, отказы с именем поля). Панель —
  вживую на тестовом стенде, на ПК и в виде телефона.

## 2.2.0 — 2026-10-27

**Журнал действий в базе, защита рассылки от отката и автоповтор, закрытые прокси и почта без
шифрования.** Обновление — копия базы, новый образ, `migrate`, затем остановить `api` и `cloudflared`
и `up -d` (README, «Обновление до 2.2»).

### Журнал действий

- **Журнал — таблица `audit_log` в базе** (модуль EAMS audit `v0.9.2`, подключён подмодулем
  `modules/audit`). Прежде журнал жил только строками ротируемого лога контейнера (5 файлов по 10 МБ),
  и поток неверных входов вытеснял строки о выгрузке ключей за несколько часов.
- Журнал **только дописывается**: `UPDATE`, `DELETE` и `TRUNCATE` отвергает сама база, даже владельцу
  схемы; строки сцеплены хешами SHA-256, раз в сутки голова цепочки пишется в лог строкой
  `audit_chain_anchor`. Срок хранения выключен — журнал хранится всегда; роль сервиса не может удалить
  его партиции, только завести новые.
- Новая команда **`verify-audit-chain`** — проверка, что журнал не переписан задним числом (0 — цел,
  2 — разрыв). Чтение — `GET /api/audit`, справочник событий — `GET /api/audit/actions`, выгрузка CSV
  или JSON — `POST /api/audit/export` (предел частоты — класс `bulk-transfer`).
- В журнал пишутся и обходы суперпользователя (каждый администратор — суперпользователь), повторные
  чтения в одной сессии сворачиваются. Проверка готовности `/api/ready` проверяет и партиции журнала.
- Строки `audit …` в логе сервиса остаются как были.
- Выгрузка сертификата и показ закрытого ключа сохраняют строку журнала **до** выдачи: не записалась —
  файл не выдаётся. Прежде строка ставилась без сохранения, и в журнале в базе она пропала бы молча.

### Рассылка

- **Защита от отката.** Старый сертификат, снова появившийся в Key Manager Plus (сканирование нашло его
  на необновлённом сервере), больше не уходит «обновлением»: сравнивается дата выпуска (`NotBefore`) с
  датой отправленного. Отправленный ещё есть — текущим остаётся он; нет — опрос не шлёт и пишет причину,
  «Отправить сейчас» шлёт как решение администратора. Продлённый досрочно сертификат с более ранним
  сроком (новые предельные сроки) — обновление и уходит. У подписок до 2.2 защита включается со
  следующей отправкой.
- **Автоповтор, если не дошло ни одно письмо** отправки (почта лежала дольше всех попыток): отметки
  снимаются, отправка повторяется тем же опросом, не больше трёх раз подряд. Не дошло части получателей —
  повтора нет, как и прежде (иначе дубли).
- **Закрытый ключ и его пароль не уходят по почте без шифрования** (`mail.smtp_security = none`):
  подписка получает отказ с объяснением; сертификаты без ключа уходят.
- Миграция `DeliveryGuards`: колонки `sent_issued`, `pending_serials`, `pending_full`, `auto_retries`.

### Защита

- **`X-Forwarded-*` — только от адреса cloudflared**, а не от всей подсети туннеля: в неё входил шлюз
  моста, то есть сам сервер, и любой процесс на нём подделывал бы адрес клиента в пределах входа и
  журнале. Адреса в сети `edge` закреплены: `SENDER_TUNNEL_PROXY_IP` (`172.31.250.2`) и
  `SENDER_TUNNEL_API_IP` (`172.31.250.3`); свой прокси — по-прежнему `SENDER_TRUSTED_PROXY_NETWORKS`.
- **Сброс доступа из переменных Portainer — один раз** на пару «адрес + пароль» (в базе — HMAC-отметка,
  набор миграций проекта `ResetAccessMarks`). Прежде забытые в стеке переменные при каждом обновлении
  снова меняли пароль и снимали аутентификатор.

### Проверено

- Тесты: 320, в том числе журнал (запись, неизменяемость, цепочка, права роли сервиса), одноразовый
  сброс, защита от отката, автоповтор, запрет ключей без шифрования. Пробный `migrate` на копии рабочей
  базы.

## 2.1.1 — 2026-10-27

**Исправления по проверке безопасности и надёжности.** Обновление — как обычно (README, «Обновление»):
копия базы, новый образ, `migrate`, `up -d`. Схема базы не меняется.

### Безопасность

- **Среда .NET в образе обновлена до 10.0.14.** Образ 2.1.0 собрался на 10.0.11 из кэша Docker: в нём
  2 критичные (подмена HTTP-запросов) и 10 высоких уязвимостей среды ASP.NET Core / .NET и одна высокая
  OpenSSL — все исправлены в свежей базе (проверено `docker scout`: 0 критичных и высоких). Сборка из
  исходников теперь — `docker compose build --pull`, в `Dockerfile` — предупреждение.
- **Сужение подписки отменяет письма, ещё стоящие в очереди:** убранный формат (например, `KEY`),
  снятый `include_passphrase`, отключение подписки — как раньше удаление подписки, получателя или
  сертификата. Прежде письмо с ключом, ждущее повтора при недоступной почте, уходило уже после того,
  как администратор передумал.
- `migrate` снова привязывает ключ API Key Manager Plus, заданный в 1.x до привязки к адресу, к
  текущему адресу — шаг потерялся при переходе на 2.0, а текст ошибки отправлял именно в `migrate`.

### Надёжность

- Сертификат подписки, который не выгрузился из Key Manager Plus (например, без закрытого ключа),
  больше не останавливает всю подписку: остальные уходят, он — в `last_error` и повторяется
  следующим опросом.
- После перерыва в опросе дольше месяца снимок больше не забывает, когда сертификат увидели впервые:
  текущим у Common Name не может стать старый сертификат.
- Нераспознанный ответ Key Manager Plus на список сертификатов — ошибка опроса, а не «ноль
  сертификатов» (иначе всем подпискам писалось бы «сертификата нет»).
- В `last_poll_error` попадает любая ошибка опроса (не открылся ключ API, сбой базы), а не только
  отказ Key Manager Plus.
- Ручная отправка большой подписки доводится до конца, даже если браузер или Cloudflare (100 с)
  оборвали запрос.
- Снимок сертификатов не «откатывает» время последнего опроса при одновременных опросе и ручной
  отправке.
- Подписку 2.0 без способа отправки можно править (убрать получателя), не выбирая способ.

### Проверено

- Тесты: 306, три прогона (Release, Debug, Release) без сбоев; найденная зависимость теста заголовков
  защиты от соседнего теста устранена. Сквозная проверка всех функций на тестовом стенде, проверка
  рабочего сервиса снаружи (заголовки, TLS, закрытость API), аудит пакетов NuGet и npm — уязвимостей нет.

## 2.1.0 — 2026-10-27

**Подписка на несколько сертификатов и письмо таблицей**, как уведомление Key Manager Plus.
Обновление — как обычно (README, «Обновление»): копия базы, новый образ, `migrate`, `up -d`.

### Подписки

- В подписке **от 1 до 50 сертификатов** (`common_names`). Один сертификат по-прежнему можно передать
  полем `common_name`, оба поля сразу — `400`. В ответе вместо `common_name` и `last_sent_serial` —
  `common_names`, `sent_serials` (какой серийный номер ушёл последним по каждому Common Name) и
  `last_full_sent_at` (последняя отправка всех сертификатов).
- **При обновлении** уходит только обновлённый сертификат, а не вся подписка. **Раз в N дней** и
  кнопкой **«Отправить сейчас»** уходят все сертификаты подписки; срок расписания считается от
  последней полной отправки.
- **Хотя бы один способ отправки обязателен** — «при обновлении» или «раз в N дней». Подписку без
  них сервис не сохранит (`400`, поле `on_change`): она молча ничего не слала бы.
- Сертификата подписки нет в Key Manager Plus — остальные уходят, в `last_error` — какого нет.
  Нет ни одного — ничего не уходит.
- Добавленный в подписку сертификат уходит ближайшим опросом — только он. Убранный из подписки
  отменяет её неотправленные письма; оставшиеся сертификаты уйдут заново.
- Панель: в форме подписки — список сертификатов с удалением и полем «Добавить»; в таблице
  рассылки — число сертификатов и ближайший срок.

### Письмо

- Сертификаты — **таблицей**: Сертификат, Форматы, Действует до, Осталось дней (без серийного номера
  и отпечатка). Колонки на языке письма — `ru`, `uk`, `en`.
- Письмо уходит **двумя частями**: HTML с таблицей и простой текст для клиентов без HTML (таблица
  строкой на сертификат). В HTML нет ссылок, картинок и внешних ресурсов; всё экранировано.
- Один архив на письмо: один сертификат — `<Common Name>.zip`, как раньше; несколько —
  `ssl-certificates.zip` с папкой на каждый сертификат, `passphrase.txt` — в папке своего.
- Тема — «SSL-сертификат имя» или «SSL-сертификаты a, b, c и ещё N».
- Виды писем — `certificate_delivery` (один сертификат) и `certificate_delivery_several`; прежние
  `certificate_delivery_1` … `_9` больше не ставятся.

### Модули

- **core `v0.10.0`, mail `v0.10.0`** — таблицы в письмах и HTML-часть (решение EAMS 0121): запись
  `MailTable`, перегрузка `IMailQueue.EnqueueAsync` с таблицами, строка-заполнитель шаблона
  `{table:имя}`, параметр подключения `Html`, колонка `mail_outbox.html_body` (миграция модуля
  `MailHtml`), HTML-часть запечатана тем же ключом данных, что и текст. По умолчанию `Html` выключен —
  у EAMS и прочих потребителей модуля письма прежние, байт в байт.
- hosting `v0.6.1`, identity `v0.10.1`, tokens `v0.8.2`, settings `v0.8.2` — только требование ядра
  0.10.0, код не менялся; crypto `v0.5.0` прежний.
- Проект включает `Html` (docs/REFERENCE.md, «Что проект задаёт модулям»).

### Обновление базы (`migrate`)

- Миграция `SubscriptionCertificates` переводит каждую подписку на список из одного её сертификата и
  переносит отправленный серийный номер и время отправки. **Повторной рассылки после обновления
  нет.** Модуль почты добавляет колонку `html_body`.
- Откат на 2.0.0 — только из копии базы.

## 2.0.0 — 2026-10-26

**Сервис переведён на модули EAMS** — модульный монолит, где каждый общий модуль живёт в своём
репозитории `danrey-bilo/module-*`. Учётные записи, сессии, настройки, почта, крипта и конвейер
запросов теперь — модули EAMS; своё у проекта — хост, модуль Key Manager Plus и панель. Обновление
с 1.x — README, «Обновление до 2.0»: **сначала копия базы**, затем `migrate`.

### Модули

- Подключены подмодулями `modules/<имя>`, только нужные проекту, каждый **закреплён коммитом метки**
  и сам не обновляется: core `v0.9.0`, crypto `v0.5.0`, hosting `v0.6.0`, identity `v0.10.0`,
  tokens `v0.8.1`, settings `v0.8.1`, mail `v0.9.0`. Переход на другую версию — только явным
  коммитом подмодуля (docs/REFERENCE.md, «Модули EAMS подмодулями»).
- Модули доработаны в EAMS так, чтобы прежнее поведение EAMS не изменилось — всё новое включается
  опциями (решение EAMS 0120):
  - **core + mail:** вложения письма, номер письма, состояние писем (ждёт / ушло / не ушло) и отмена
    неотправленных; виды писем вне предела частоты; рамка письма (приветствие и подпись с именем
    продукта, `Frame`) и привязка пароля SMTP к серверу (`BindSmtpPassword`);
  - **hosting:** окно свежего кода второго фактора — из настройки, в отказе `details.window_minutes`;
  - **identity:** настройка `auth.step_up_minutes`, поле `step_up_until`, проверка ссылки активации
    POST-ом, восстановление доступа из консоли одной транзакцией и опции входа: код письмом не
    заменяет приложение, сессия настройки аутентификатора для всех, кука обновления не уходит в тело,
    предел кодов на попытку входа, «последний администратор» — только способный войти, ограничитель
    параллельного хеширования паролей.
- Удалены собственные `EmailSslSender.Shared`, `EmailSslSender.Modules.{Identity,Tokens,Settings,Mail}`
  и их тесты: их место заняли модули. Модуль Key Manager переведён на контракты ядра модулей
  (`Modules.Core`, `Modules.Crypto`) и несёт свой набор миграций.
- Что проект задаёт модулям опциями (имя куки, издатель TOTP, обязательный аутентификатор, имя
  сервиса в письмах, выключенные подвозможности — ключи интеграции, доверенные браузеры, расширение,
  справочник людей) — таблица в docs/REFERENCE.md, «Что проект задаёт модулям».

### Перенос данных (`migrate`)

- Прежние миграции хоста дотягиваются до моста **`ModulesBridge`**: недостающие колонки, ограничения
  и индексы схемы модулей, таблица `user_preferences`; каждая учётная запись становится
  суперпользователем (ролей нет, администраторы равны). Базовые миграции модулей отмечаются
  применёнными, остальные выполняются; у каждого модуля своя таблица истории `__ef_history_<модуль>`.
- **Секреты перекладываются** в конверт модулей тем же мастер-ключом: секреты TOTP, пароль SMTP,
  ключ API Key Manager Plus. Идемпотентно; повторный `migrate` ничего не меняет.
- Неотправленные письма (тела запечатаны прежним конвертом) отмечаются неотправленными.
- Набор миграций проекта задаёт окно свежего кода **10 минут** (умолчание модуля — 5) и на новой, и
  на обновлённой установке.
- Проверено на копии живой базы: все секреты переложены, схема совпадает со схемой новой установки;
  тест `ModulesBridgeTests` держит это сравнением каталога.

### Что изменилось для администраторов

- После обновления **все входят заново**; ссылки приглашений и сброса пароля, выданные до обновления,
  не действуют — выдайте снова.
- **Свежий код спрашивают чаще:** правка любой настройки (не только защиты), правка учётной записи
  (и имени), проверочное письмо, смена своего пароля. Панель спрашивает код сама.
- Новые пользователи из панели заводятся суперпользователями — как и прежде, каждый администратор.
- `GET /api/activation?token=` по-прежнему закрыт (`405`): ссылка приглашения передаётся телом
  запроса; модуль держит этот путь ради клиентов EAMS, хост его закрывает.
- Письмо с сертификатом — прежнего вида: список файлов в архиве — по строке на файл. Модуль почты
  вырезает переводы строк из подставляемых значений, поэтому вид письма выбирается по числу файлов
  (`certificate_delivery_1` … `_9`).
- Журнал (`audit` в логе): значения изменений — у настроек и Key Manager Plus, у прочих событий —
  имена полей; отказы в праве — строкой `authz.denied`.
- В образе нет ничего нового снаружи: тот же `docker compose`, те же переменные и секреты.

### Сборка

- Клонировать с подмодулями: `git clone --recurse-submodules`. Репозитории модулей закрытые.
- Сборка образа в GitHub Actions забирает подмодули секретом **`MODULES_TOKEN`** (fine-grained токен,
  `Contents: Read-only` на `email_ssl_sender` и семь `module-*`).
- В `Directory.Packages.props` — пакеты, нужные модулям сверх наших: BouncyCastle.Cryptography,
  Npgsql, Serilog, StackExchange.Redis (последний — только для сборки модуля хостинга, Redis сервис
  не использует). Модули собираются по правилам проекта.
